# Интеграции

Порядок волн и что известно о каждой платформе. **Все условия API ниже не проверены по актуальной
документации** и записаны как ориентир. Перед реализацией каждой интеграции:

1. Открыть официальную документацию, проверить способ авторизации, webhooks, лимиты, цены, условия.
2. Обновить раздел этой платформы: ссылки на документацию, дата проверки, что подтвердилось.
3. Только после этого писать код.

Статусы: ⬜ не начато · 🟨 документация проверена · 🟩 работает.

## Волна 1: мессенджеры

### Telegram (Bot API) ⬜ первый канал

- Компания создаёт бота у @BotFather и вставляет токен в настройках CRM.
- Входящие: webhook (основной вариант) или long polling `getUpdates` для разработки.
  Ожидается возможность передать секрет при регистрации webhook и проверять его в заголовке
  запроса. *Проверить.*
- Сценарий: сообщение покупателя → контакт (по Telegram user id) → диалог во «Входящих» →
  менеджер отвечает из CRM → кнопка «Создать заявку» из диалога.
- Проверить: лимиты частоты отправки, работа с файлами и их размером, правила для ботов
  (бот не может написать первым, пока пользователь не начал диалог).
- Документация: https://core.telegram.org/bots/api

### Instagram (Meta Graph API) ⬜

- Директ и комментарии. Нужен бизнес/профессиональный аккаунт, связанный со страницей Facebook,
  и проверка приложения Meta (App Review) для нужных разрешений. Это занимает время, подавать заранее.
- Проверить: актуальные разрешения, окно ответа на сообщения, webhooks, требования к политике
  конфиденциальности и удалению данных.
- Документация: https://developers.facebook.com/docs/instagram-platform

### WhatsApp Business API ⬜

- Через официальный WhatsApp Business Platform (Cloud API) напрямую или через провайдера (BSP).
- Проверить: какой провайдер работает с Узбекистаном, модель оплаты (за диалоги/сообщения),
  шаблоны сообщений и окно ответа, верификация бизнеса.
- Документация: https://developers.facebook.com/docs/whatsapp

## Волна 2: местная специфика

### Платежи: Click, Payme, Uzum ⬜

- Два сценария: (а) оплата подписки нашей CRM, (б) клиенты CRM выставляют счета своим покупателям.
- Проверить у каждой: договор с мерчантом, протокол (у Click и Payme свои протоколы с обратными
  вызовами), проверка подписи, тестовая среда, фискализация чеков.
- Документация: брать только с официальных сайтов и из кабинета мерчанта.

### SMS: Eskiz, PlayMobile ⬜

- Проверить: авторизация, регистрация имени отправителя, требования к шаблонам, статусы доставки
  (callback), цены.

### IP-телефония ⬜

- Запись звонков и привязка к карточке клиента по номеру.
- Проверить, какие АТС/операторы популярны у клиентов (облачные АТС местных операторов, Asterisk и т. п.),
  какие у них webhooks/API, где хранятся записи и как долго.

## Волна 3

### Google Sheets и Calendar ⬜
OAuth 2.0 на пользователя. Проверить требования к проверке приложения Google для нужных scope.
Учесть трансграничную передачу данных (см. хостинг в `architecture.md`).

### Почта (IMAP/SMTP) ⬜
Учётные данные почтового ящика компании в хранилище секретов, polling IMAP через воркер.

### Экспорт в Excel ⬜
Генерация .xlsx на сервере. Библиотеку выбрать с permissive-лицензией (например, openpyxl, MIT;
*проверить при добавлении*).

### Открытый API и webhooks ⬜
REST API с ключами на компанию и правами, исходящие webhooks с подписью HMAC и повторами.
Документация OpenAPI генерируется FastAPI.

### 1С ⬜
Проверить варианты обмена: OData-интерфейс 1С, HTTP-сервисы, обмен файлами (XML/EnterpriseData).
Выбор зависит от конфигурации у клиента.

### Odoo (внешняя система клиента) ⬜

Требования от владельца (уточнить по документации Odoo при реализации):

- Odoo 19+: JSON-2 API; Odoo 17 и 18: XML-RPC.
- Авторизация API-ключами; на каждую интеграцию отдельный технический пользователь Odoo.
- На Odoo Online внешний API доступен только на тарифе Custom; предупреждать клиента при подключении.
- Синхронизация: контакты `res.partner`, лиды и сделки `crm.lead`, статусы (этапы).
- Соответствие ID через `external_refs`, определение изменений по дате записи и `hash`.

## Общие требования (для всех коннекторов)

- Единый интерфейс коннектора, модуль-плагин на платформу (см. `architecture.md`).
- Входящие и исходящие через очередь с повторами; идемпотентность по внешним ID.
- Секреты только из окружения/хранилища, никогда в коде и логах.
- Каждая используемая SDK-библиотека платформы проверяется по лицензии и вносится в `licenses.md`.
