# Архитектура

Документ описывает целевую архитектуру. Что уже реализовано, отмечено в разделе «Текущее состояние».

## Текущее состояние

- Один модуль «Заявки» (`leads`): модель, JSON API (`/api/leads`, `/api/statuses`), React-страница.
- FastAPI раздаёт собранный фронтенд из `frontend/dist`; в Docker один образ приложения и PostgreSQL.
- Мультиарендности, пользователей и коннекторов пока нет.

## Общая схема

```
 Браузер (React)          Внешние платформы (Telegram, Meta, платёжки, SMS, АТС)
       │ JSON                  │ webhooks                 ▲ исходящие
       ▼                       ▼                          │
 ┌──────────────────────── FastAPI (app) ──────────────────────────┐
 │  /api/...  (интерфейс)     /hooks/<коннектор>/<id> (входящие)    │
 │  modules: contacts, leads, deals, pipelines, tasks, inbox, ...   │
 │  connectors: base, registry, telegram, instagram, whatsapp, ...  │
 └───────────────┬──────────────────────────────┬───────────────────┘
                 │ SQL (RLS по company_id)      │ задачи
                 ▼                              ▼
            PostgreSQL                 Valkey ──► Celery workers
                                                  (синхронизация, повторы, рассылки)
```

Webhook-обработчик только проверяет подпись, сохраняет сырое событие и ставит задачу в очередь.
Вся тяжёлая работа (нормализация, поиск контакта, запись в историю) идёт в воркере. Так внешняя
платформа получает быстрый ответ, а сбой обработки не теряет событие.

## Мультиарендность (облачная подписка)

- **Модель**: одна база, общие таблицы, у каждой записи клиента колонка `company_id` (FK на `companies`).
- **Слой приложения**: контекст компании определяется из сессии пользователя (или из ключа API /
  адреса webhook) и автоматически добавляется во все запросы через общий репозиторий/сессию.
- **Слой БД**: политики PostgreSQL Row-Level Security по `current_setting('app.company_id')`,
  который приложение выставляет в начале транзакции. Даже ошибка в коде не откроет чужие данные.
- **Уникальность**: индексы и ограничения включают `company_id` (например, телефон уникален в компании).
- **Пользователи**: `users` + `memberships(user_id, company_id, role)`; роли на старте: владелец,
  администратор, менеджер.
- **Тарифы**: `plans` и `subscriptions` (лимиты пользователей, каналов, контактов, пробный период).
  Проверка лимитов в сервисном слое. Оплата подписки через местную платёжку (волна 2).
- **Тесты**: для каждого модуля тест «компания A не видит и не меняет данные компании B».

## Доменная модель (план)

| Сущность | Ключевые поля |
|---|---|
| `companies` | название, тариф, статус подписки, часовой пояс (по умолчанию Asia/Tashkent) |
| `contacts` | имя, телефоны, мессенджеры, ответственный, теги |
| `leads` | контакт, источник (канал), статус, ответственный |
| `pipelines`, `stages` | воронки и этапы компании, порядок |
| `deals` | контакт, воронка, этап, сумма (UZS), ответственный |
| `tasks` | что сделать, срок, исполнитель, связь с контактом/сделкой |
| `activities` | лента истории: сообщения, звонки, смены статусов, заметки |
| `conversations`, `messages` | диалоги из каналов, направление, вложения, сырой payload (JSONB) |
| `channel_accounts` | подключённый канал компании (например, бот Telegram), ссылка на секрет |
| `external_refs` | соответствие внутренних и внешних ID (см. ниже) |

## Коннекторы

Каждый коннектор живёт в `app/connectors/<имя>/` и регистрируется в `registry.py`. Ядро знает
только интерфейс, поэтому новую платформу можно добавить, не меняя модули CRM.

Интерфейс (набросок, уточняется при реализации Telegram):

```python
class Connector(Protocol):
    name: str  # "telegram"
    # INBOUND_WEBHOOK, POLLING, SEND_MESSAGE, SYNC_CONTACTS...
    capabilities: set[Capability]

    # Проверить учётные данные, зарегистрировать webhook.
    async def connect(self, account: ChannelAccount) -> None: ...
    async def disconnect(self, account: ChannelAccount) -> None: ...
    def verify_webhook(self, request: RawRequest, account: ChannelAccount) -> bool: ...
    # Нормализация в общий формат.
    def parse_inbound(self, payload: dict) -> list[InboundEvent]: ...
    async def poll(self, account: ChannelAccount, cursor: str | None) -> PollResult: ...
    async def send(self, account: ChannelAccount, msg: OutboundMessage) -> ExternalId: ...
```

Общие форматы: `NormalizedContact` (имя, телефон в E.164, внешний ID, username) и
`NormalizedMessage` (диалог, направление, текст, вложения, время, внешний ID).

### Очередь, повторы, идемпотентность

- Входящие: сырое событие сохраняется в `inbound_events` с уникальным ключом
  `(channel_account_id, external_event_id)`; повторная доставка того же события игнорируется.
- Исходящие: запись `outbound_messages` со статусом и ключом идемпотентности создаётся до отправки;
  воркер отправляет и сохраняет внешний ID. Повтор задачи не отправляет сообщение дважды.
- Повторы с экспоненциальной задержкой и ограничением числа попыток; после исчерпания событие
  уходит в статус «ошибка» и видно в интерфейсе администратора. Лимиты частоты каждой платформы
  учитываются в коннекторе.

### Таблица `external_refs`

`(company_id, connector, entity_type, internal_id, external_id, external_account, synced_at, hash)`,
уникальность по `(company_id, connector, external_account, entity_type, external_id)`.
`hash` позволяет не отправлять запись повторно, если она не менялась (важно для Odoo, Sheets, 1С).

### Секреты

Токены каналов не хранятся в открытом виде: в `channel_accounts` лежит ссылка на секрет, сами
значения в хранилище секретов или зашифрованы ключом из переменной окружения. Логирование
проходит через фильтр, маскирующий токены; в API токены показываются как `••••1234`.

## Безопасность и хостинг

- Хостинг на серверах в Узбекистане (требование закона о персональных данных, **проверить у юриста**:
  какие данные, нужна ли регистрация базы, требования к трансграничной передаче, например при
  использовании Meta или Google).
- HTTPS везде, webhooks с проверкой подписи/секрета платформы.
- Резервные копии PostgreSQL, журнал действий пользователей (кто что изменил).
